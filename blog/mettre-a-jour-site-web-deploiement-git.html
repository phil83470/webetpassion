Mettre à jour un site web et déployer du code rectifié en toute sécurité

Par Philippe Jireau (Web & Passion) • Publié le 23 novembre 2026 • Temps de lecture : 8 min

Corriger une page, ajuster une feuille de style ou déployer une nouvelle fonctionnalité ne devrait jamais mettre votre site en péril. Ce guide détaille comment articuler Git, GitHub, votre éditeur de code et les outils d'un hébergeur comme o2switch pour publier vos mises à jour sans perte de données.

L'essentiel avant de commencer

Publier directement un fichier depuis votre ordinateur vers le serveur fonctionne pour une retouche isolée, mais laisse votre code sans historique. Associer Git et GitHub comme mémoire centrale, puis déployer via SFTP, SSH ou Git™ Version Control (cPanel) vous garantit de pouvoir annuler n'importe quelle erreur en quelques secondes.

1. Git et GitHub : stockage, versionnement et filet de sécurité

Lorsque vous modifiez le code d'un site web directement sur le serveur en production, la moindre faute de syntaxe écrase immédiatement la version qui fonctionnait. Pour éviter ce scénario, les développeurs séparent l'environnement où le code est écrit de l'environnement où il est stocké, puis de celui où il est exécuté.

Trois rôles complémentaires pour protéger votre projet

Git (sur votre machine)
Enregistre l'évolution des fichiers dans le temps. Chaque ajout, suppression ou correction est figé sous forme d'un commit daté et commenté. Vous pouvez comparer deux états ou revenir à une version antérieure saine à tout moment.
GitHub / GitLab (dans le cloud)
Sert de dépôt distant central (source principale) et de sauvegarde hors-site. Si votre ordinateur tombe en panne ou si une manipulation détruit un dossier sur l'hébergement, l'intégralité du code et de son historique reste intacte en ligne.
JetBackup (sur l'hébergeur)
Complète Git côté serveur : o2switch sauvegarde automatiquement vos fichiers, bases de données et emails (conservés 30, 45 ou 90 jours selon l'offre). C'est votre second filet de sécurité pour restaurer un site complet ou une base SQL en cas d'incident.

En résumé : Git ne remplace pas la sauvegarde serveur (qui protège aussi votre base de données et vos fichiers médias téléversés par les visiteurs), et JetBackup ne remplace pas Git (qui conserve chaque ligne de code modifiée avec son auteur et sa justification). Les deux mécanismes se complètent.

2. Comment se connecter et mettre à jour son site sur un hébergeur (type o2switch)

Pour acheminer vos fichiers rectifiés jusqu'à l'espace web de votre hébergement, trois grandes voies existent : le transfert de fichiers sécurisé (SFTP/FTPS), l'outil graphique Git de cPanel et la ligne de commande SSH.

2.1 Transfert sécurisé de fichiers : FTP, FTPS et SFTP (FileZilla)

Bien que leurs noms se ressemblent, ces trois protocoles offrent des niveaux de sécurité radicalement différents.

Protocole Chiffrement Port Verdict
FTP (File Transfer Protocol) Aucun — identifiants et fichiers en clair 21 À éviter
FTPS (FTP Secure) SSL/TLS en mode explicite 21 Acceptable
SFTP (SSH File Transfer Protocol) SSH natif intégral dès l'ouverture 22 Recommandé

Inspecteur interactif : que circule-t-il sur le réseau ?

Sélectionnez un protocole pour observer le comportement de la connexion (notamment sur un réseau Wi-Fi public) et les réglages à appliquer dans FileZilla.

Paramètres SFTP sur FileZilla pour o2switch : sélectionnez le protocole SFTP - SSH File Transfer Protocol, renseignez votre domaine (ou l'adresse serveur qqch.o2switch.net de votre email de bienvenue), utilisez le type d'authentification Normale avec votre identifiant et mot de passe cPanel (le SFTP n'est pas disponible sur les comptes FTP secondaires), et laissez le port sur 22. Au préalable, votre adresse IP doit être ajoutée dans l'outil Autorisation SSH de cPanel.

Alternatives cPanel : Gestionnaire de fichiers et comptes FTP secondaires

Sans installer FileZilla, le Gestionnaire de fichiers de cPanel permet de naviguer dans vos répertoires, téléverser un fichier ou modifier du code directement depuis le navigateur. Si vous travaillez avec un prestataire externe, vous pouvez également créer un compte FTP secondaire limité à un seul sous-dossier afin de ne pas partager votre mot de passe cPanel principal (ce compte fonctionnera en FTPS explicite plutôt qu'en SFTP).

2.2 L'outil Git™ Version Control de cPanel et Gitweb

cPanel intègre une surcouche graphique nommée Git™ Version Control. Elle permet de gérer des dépôts sur votre hébergement, de consulter l'historique des commits via l'interface web Gitweb (bouton History) et d'automatiser la mise en ligne grâce au hook post-receive et au fichier .cpanel.yml.

Deux architectures sont possibles lors de la création du dépôt dans cPanel :

  • Dépôt local principal (case Clone a repository décochée) : l'hébergement reçoit directement vos commits. Depuis votre ordinateur, vous liez votre dossier local via git remote add origin ssh://identifiant@serveur/chemin (ou vous le clonez avec git clone) puis vous exécutez git push -u origin master.
  • Miroir d'un dépôt externe GitHub / GitLab (case Clone a repository cochée) : c'est l'approche recommandée si vous utilisez GitHub comme filet de sécurité. L'URL doit commencer par https://, ssh://, http:// ou git:// et ne doit jamais contenir de paire identifiant:motdepasse.
Dépôt privé sur GitHub : deux paires de clés SSH à ne pas confondre

Pour cloner un dépôt privé, le protocole ssh:// est obligatoire. Vous devez configurer deux autorisations distinctes :

  • Connexion A (Votre ordinateur → Hébergement) : votre clé publique locale dans ~/.ssh/authorized_keys sur l'hébergement.
  • Connexion B (Hébergement → GitHub/GitLab) : une clé privée dédiée dans ~/.ssh/id_rsa sur l'hébergement, dont la clé publique est ajoutée dans les réglages SSH de votre compte GitHub, avec autorisation pare-feu côté hébergeur (GitHub est généralement déjà en liste blanche sur o2switch ; pour GitLab, contactez le support en cas de timeout).

Déploiement PUSH vs PULL et règle d'or du fichier .cpanel.yml

Dans cPanel, deux modes de déclenchement existent. En mode PUSH, pousser directement vers l'hébergement déclenche automatiquement le script de déploiement. En mode PULL (avec GitHub), vous poussez d'abord votre code vers GitHub, puis vous ouvrez cPanel → Gérer → onglet Pull or Deploy pour cliquer sur Update from Remote (récupère le code via git pull) puis sur Deploy Head Commit.

Dans les deux cas, deux prérequis stricts s'appliquent : un fichier .cpanel.yml valide à la racine du dépôt Git, et un espace de travail Git propre sur l'hébergement (git status ne doit signaler aucune modification locale en attente, sinon cPanel refuse le déploiement).

2.3 L'accès SSH en ligne de commande

Vous n'êtes pas obligé de passer par l'interface graphique de cPanel : l'accès SSH vous ouvre directement un terminal sur votre hébergement pour exécuter git, manipuler des archives, lancer mysqldump, utiliser wp-cli, ou piloter des environnements Node.js, Python ou Ruby.

  1. Débloquer votre IP dans le pare-feu : ouvrez l'outil Autorisation SSH dans cPanel et ajoutez votre adresse IP (5 exceptions maximum). Si votre box change d'IP, utilisez un service DynDNS gratuit (comme No-IP) : l'hébergeur met à jour l'autorisation automatiquement en 3 à 5 minutes. Une erreur timeout signifie presque toujours que votre IP n'est pas en liste blanche.
  2. Choisir votre mode de connexion : via le navigateur avec l'outil Terminal de cPanel (connexion automatique), par mot de passe sur le port 22 (ssh identifiant@serveur.o2switch.net), ou par clé SSH sans mot de passe.
  3. Configurer l'authentification par clé SSH (recommandé) : générez une paire de clés avec ssh-keygen -t rsa -b 4096 (ou avec PuTTYgen en mode SSH-2-RSA sur Windows, en veillant à le télécharger uniquement sur le site officiel). Copiez le contenu de id_rsa.pub dans ~/.ssh/authorized_keys sur le serveur.
Droits Unix indispensables pour que la clé SSH soit acceptée

Par sécurité, le serveur SSH refuse automatiquement toute clé si les permissions sont trop larges. Vérifiez ces quatre réglages :

  • Dossier ~/.ssh : chmod 700
  • Fichier authorized_keys sur le serveur : chmod 644
  • Clé publique .pub : chmod 644
  • Clé privée id_rsa sur votre poste : chmod 400
Ce que l'accès SSH permet — et ce qui reste interdit en hébergement mutualisé

Autorisé : commandes git, manipulation de fichiers et d'archives (zip, tar.gz), export de base de données (mysqldump), scripts bash/Python, consoles de frameworks (Symfony, Laravel, virtualenv Python, Ruby, Node.js/npm), outils CMS (WP-CLI, Drush).

Interdit : installer des paquets système (apt-get, yum), lancer des conteneurs Docker ou des machines virtuelles, modifier le pare-feu ou la configuration globale du serveur web (tout ce qui requiert les droits root).

3. Mettre à jour directement depuis l'éditeur de code (IDE)

Que vous utilisiez Antigravity, VS Code ou un éditeur similaire, vous n'avez pas besoin de basculer sans cesse entre votre code et un logiciel tiers comme FileZilla. Votre éditeur propose deux mécanismes directs : l'extension de transfert SFTP et le terminal intégré.

Méthode A — Plugin ou extension d'upload SFTP direct

Les extensions SFTP intégrées à l'IDE (configurées via un fichier JSON local de projet) relient votre dossier de travail à un répertoire précis sur le serveur en utilisant le protocole SFTP sur le port 22.

  • Fonctionnement : vous déclenchez manuellement l'envoi du fichier modifié (clic droit → Upload) ou vous activez l'envoi automatique à chaque sauvegarde (uploadOnSave).
  • Sécurité de configuration : utilisez impérativement le protocole sftp (jamais ftp), votre identifiant cPanel ou votre clé privée SSH, et excluez les dossiers sensibles (.git, node_modules, fichiers de configuration locaux contenant vos mots de passe) de la synchronisation.
  • Point de vigilance : avec uploadOnSave activé, une faute de frappe enregistrée par réflexe (Ctrl+S) part immédiatement en production. Ne l'activez jamais sur un site actif sans copie locale versionnée.

Méthode B — Le terminal intégré à l'éditeur

La quasi-totalité des éditeurs modernes intègrent un terminal système (raccourci clavier ou panneau inférieur). C'est l'outil le plus polyvalent, car il vous permet de piloter Git ou d'envoyer des fichiers sans quitter votre code : 

# 1. Vérifier les fichiers modifiés avant tout envoi
git status

# 2. Enregistrer la rectification dans l'historique Git local
git add chemin/du/fichier.html
git commit -m "Correctif affichage menu mobile"

# 3. Envoyer vers votre sauvegarde GitHub (ou directement vers cPanel)
git push origin main

Si vous devez pousser ponctuellement un dossier compilé (par exemple un dossier dist/ ou des assets statiques) par-dessus SSH sans passer par un dépôt distant, le terminal de l'IDE permet aussi d'exécuter une synchronisation différentielle chiffrée via rsync -avz -e ssh, beaucoup plus rapide que de renvoyer tout le site fichier par fichier.

4. Comparatif étape par étape : Déploiement Direct vs Workflow Sécurisé

Faut-il toujours passer par GitHub pour corriger une simple faute d'orthographe, ou peut-on parfois déployer en direct ? Comparez ci-dessous le déroulement concret des deux méthodes et leur comportement lorsqu'un incident survient en production.

Explorateur étape par étape des deux workflows

Cliquez sur une étape pour comparer exactement ce qui se passe entre le déploiement direct rapide et le workflow recommandé sécurisé (IDE → GitHub → Hébergeur).

Tableau décisionnel : quelle méthode choisir ?

Critère Déploiement Direct (SFTP / IDE) Workflow Sécurisé (IDE → GitHub → Hébergeur)
Vitesse sur 1 fichier isolé Immédiate (quelques secondes) Rapide (1 commit + 1 push + pull/deploy)
Historique & traçabilité Aucun — le fichier précédent est écrasé Complet (auteur, date, diff ligne par ligne)
Travail en équipe Risque élevé d'écraser le code d'un collègue Fusion contrôlée via GitHub
Retour arrière sur erreur Manuel ou restauration globale JetBackup Instantané via git revert + redéploiement
Usage conseillé Dépôt d'un média, hotfix trivial sur site statique Toute évolution de code, thème, plugin ou application

Procédure complète du Workflow Recommandé (IDE → GitHub → cPanel)

  1. Rectifiez et testez localement dans votre éditeur de code.
  2. Validez la modification dans Git : dans le terminal intégré, exécutez git status, puis git add sur les fichiers concernés et git commit -m "Description claire du correctif".
  3. Synchronisez vers GitHub : lancez git push origin main. Votre code rectifié est désormais sauvegardé et historisé hors de votre machine.
  4. Mettez à jour l'hébergement : dans cPanel → Git™ Version Control → Gérer → Pull or Deploy, cliquez sur Update from Remote pour importer le dernier commit depuis GitHub.
  5. Déployez en production : cliquez sur Deploy Head Commit (exécute votre fichier .cpanel.yml). Vérifiez ensuite votre site public dans un onglet de navigation privée.
